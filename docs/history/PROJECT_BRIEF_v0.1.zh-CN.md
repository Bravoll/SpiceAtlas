# 香草与香辛料图文百科：需求梳理与分阶段方案 v0.1

日期：2026-10-27（墨尔本）  
暂定项目名：Spice Atlas／香料图鉴  
文件性质：项目设计说明；包含建议、示例与待核实字段，不代表网站、采集器或翻译接口已实现。

## 1. 项目的目标

建立一个以中文阅读为主的本地香草与香辛料知识库，帮助使用者从“不认识一种香料”逐步了解其名称、外观、使用部位、风味、种植地区、饮食文化、代表菜品和商品形态。

网站承担日常查询、比较和阅读；以后可以从整理过的条目导出科普视频所需的章节、事实说明、图片清单和出处。

当前阶段先确定分类、条目模板、内容来源和实施顺序。视频制作放在知识库内容相对稳定之后。

### 用户已表达的需求

| 需求 | 建议落实方式 |
| --- | --- |

| 代表菜品 | 菜品实体，关联香料、形式和参考食谱 |

## 2. 首先明确“香料”这个范围

本项目中的“香料”指烹饪使用的香草与香辛料，初期以植物来源为主。

英文里 Herbs 通常指作为调味材料使用的叶、嫩梢等；Spices 常指果实、种子、树皮、根茎、花蕾等。它们是烹饪中的常见用语，不能代替植物分类；同一种植物可以贡献不同类型的调味材料。例如芫荽的叶和成熟干果都用于烹饪。[S1]

第一版可以把复合调味料预留为独立类别，例如 curry powder 和五香粉。它们的配方可能随地区、家庭和品牌变化，不能作为单一植物处理。盐、动物来源调味料和食品添加剂是否纳入，可留待以后决定。

## 3. 最重要的数据关系

### 3.1 区分四类对象

| 对象 | 回答的问题 | 示例 |
| --- | --- | --- |
| 植物／物种 | 这是什么植物？ | 欧芹、芫荽、芹菜 |
| 调味原料与使用部位 | 用的是哪一部分？ | 欧芹叶、芫荽叶、芫荽干果 |
| 加工形态 | 它被加工成什么？ | 鲜叶、干叶碎、整粒、粗碎、粉末 |
| 商品／包装实例 | 这个具体产品怎么卖？ | 某品牌某地区出售的玻璃瓶装欧芹碎 |

对于芫荽，市售的 coriander seed 通常指其干燥果实，数据库可以同时保留“烹饪名称：籽”和“植物学部位：果实”。[S1]

Parsley flakes 是欧芹的一种加工形态。已核实的 McCormick 产品页将它描述为干燥欧芹叶，并展示瓶装商品；该页不能证明所有欧芹碎都使用同一种包装。[S2]

### 3.2 混合物另建关系

复合调味料关联多个原料，配方版本另存。不要把“意式香草混合料”等同于一个物种。

菜品也关联具体原料和形态。例如 Tabbouleh 的已核实参考食谱使用切碎的平叶欧芹。[S3] 不能据此把食谱中的鲜欧芹自动替换成干欧芹碎。

### 3.3 “类似”必须有可解释的关系

| 关系 | 页面如何解释 | 不应自动推断的内容 |
| --- | --- | --- |
| 同科／同属 | 具有植物分类关系 | 味道相同、能直接替代 |
| 同一植物的不同部位 | 例如芫荽叶与芫荽干果 | 具有相同的香气组成 |
| 外观相似 | 需要区分的原料 | 属于同一种植物 |
| 风味接近 | 某些风味描述有重叠 | 在所有菜品中可替换 |
| 烹饪用途相近 | 都用于某类汤、酱汁等 | 文化背景或使用方法相同 |
| 常在同一道菜中出现 | 某个有出处的共同使用例 | 二者彼此相似 |
| 可替代 | 指定菜品、部位、形态和用量条件 | 无条件的一比一替换 |

例如，欧芹、芫荽与芹菜均可放入伞形科这一植物分类视图。[S4] 搜索“芹菜”时，网站可以显示这些相关条目，并说明“同为伞形科”；不要仅凭名称含有“芹”字建立关系。

## 4. 分类目录：一套主目录，多个筛选维度

建议主目录按照烹饪使用部位安排，以便初学者浏览。一个植物可以出现在多个部位类别中。

| 主目录 | 示例候选 |
| --- | --- |
| 叶与嫩梢 | 欧芹、罗勒、牛至、百里香、迷迭香 |
| 果实与种子 | 黑胡椒、芫荽籽、孜然、茴香 |
| 花与花蕾 | 丁香等 |
| 树皮 | 肉桂等 |
| 根与根茎 | 姜、姜黄等 |
| 复合调味料 | 咖喱粉、五香粉等，单独处理配方 |

这里是浏览目录的设计示例，并非完整的植物学分类表。具体条目的使用部位在录入时逐项核实。

并行筛选维度：

- 植物分类：科、属、种，必要时加入栽培品种或商品类型。
- 风味：草本、柑橘样、木质、辛辣、甘甜等，允许多个标签并记录来源。
- 饮食文化／地区／菜系：允许多选，避免将一种原料限定为单一国家所有。
- 使用方式：生用、炖煮、烘焙、腌制、煎炒、装饰等。
- 加工形态：鲜品、干燥、整粒、碎、粉等。
- 内容状态：已有摘要、已有原文、已有翻译、已人工核实、待补充图片等。

“固定目录”指本地控制条目和导航的版本，不是永久禁止扩充，也不意味着直接复制维基百科的分类树。

## 5. 一份条目应该回答什么

### 5.1 固定条目模板

| 模块 | 应保存的信息 |
| --- | --- |
| 身份 | 本地稳定 ID、中文名、英文名、学名、别名与适用地区 |
| 认识它 | 一句话介绍、属于哪类原料、最容易混淆的对象 |
| 图片 | 整株、使用部位、干燥品／粉末、包装、菜品 |
| 使用部位 | 叶、茎、根、果实、种子、树皮、花等 |
| 加工形态 | 鲜品、干叶碎、整粒、粗碎、粉末、其他 |
| 原料组成 | 单一原料或混合配方；配料表对应具体商品 |
| 香气与味道 | 感官描述；有证据时补充相关化合物 |
| 营养信息 | 鲜／干样品、单位和来源；有需要再加入 |
| 地理 | 原生分布、栽培地区、商业产区，各自记录 |
| 饮食文化 | 地区与菜系、具体使用部位和烹饪方法 |
| 代表菜品 | 菜名、地区说明、用量／做法参考来源 |
| 包装 | 商品实例的容器、材质、规格、地区、观察日期 |
| 相关条目 | 关系类型、理由、出处或编辑说明 |
| 正文来源 | 来源名称、原语言、标题、URL、获取时间、版本 |
| 阅读模式 | 原文、译文、双语；译文模型与生成记录 |
| 引用 | 能追溯到具体来源与段落的标记 |

### 5.2 “成分”分成三类

1. **原料组成**：例如某瓶产品是否只有欧芹，或是否含盐、其他香草与辅料。以对应商品配料表为准。
2. **香气／呈味化合物**：例如芫荽籽精油中经研究识别的芳樟醇（linalool）。记录研究样本、植物部位、方法和出处。[S5]
3. **营养组成**：例如每 100 g 鲜叶或干叶的营养数据。不同基准的数据分开显示。

精油中某化合物的占比不等于整份食材的质量占比。叶与籽的化学组成也不能互相代用。[S5] 第一版先写主要风味和原料身份；化合物作为可展开的进阶内容。

### 5.3 “在哪里种植”分成三类

- **原生分布**：植物本身的自然分布，允许不确定或有争议的结论。
- **栽培地区**：有人种植，可以是长期广泛栽培，也可以只是适合当地园艺。
- **商业生产地区**：涉及生产量、出口量或排名时，必须记录年份和统计口径。

例如，印度香料委员会列举了芫荽的多个商业生产地区。[S6] 这一名单不能当作当前年度产量排名。

| 来源 | 适合承担的角色 | 接入策略 |
| --- | --- | --- |
| 中文维基百科 | 中文条目、章节和原有参考文献 | 第一批自动接入 |
| 英文维基百科 | 中文覆盖不足时补充另一份来源 | 第二批接入，保留独立版本 |
| Wikimedia Commons | 有可核查出处与许可的图片 | 第一批接入 |
| Wikidata | 跨语言名称、条目链接与外部标识 | 辅助身份匹配，匹配结果需检查 |
| 植物园／植物分类数据库 | 学名、植物分类和分布核对 | 先人工核对与记录链接 |
| 农业研究机构／官方推广资料 | 栽培与生产背景 | 选择性引用，按资料条件接入 |

中文优先是默认显示策略，不是将不同语言文章视为同一文本。中文条目简短时，可以并列显示英文来源的翻译补充，并标明来源。

Gernot Katzer 的条目按名称、使用部位、植物科、风味、化学、来源等组织，较接近本项目想学习的内容结构。[S8] 商业网站和个人参考网站的文字与图片，需要分别确认其复用条件；默认先作为参考与外链。

本次无法通过检索工具读取此前提到的 Spices Inc 博客路径，因此不把该路径列为已经确认的自动接入源。A–Z 索引已成功读取。网站可读不等于有公开 API 或允许全文复制。

### 7.3 本地目录与外部内容怎样配合

1. 本地目录里预置名称、分类、别名、条目 ID 和核实过的来源指向。
2. 打开条目时先读本地缓存。
3. 尚未获取的来源显示“可获取”，用户点击后由本地后台获取。
4. 原文、版本、图像元数据与翻译各自保存。
5. 外部来源更新时提示可更新；先保留已有原文与译文。
6. 只有来源版本或翻译配置改变时，才需要重新翻译相应内容。

已缓存并完成本地化的内容可离线阅读。未缓存的正文、远程图片和更新检查仍需要联网。

## 8. 维基正文、章节、引用与图片怎么接入

### 8.1 建议使用的接口路线

以每个站点的 MediaWiki Action API 为第一版接入方式，例如：

- 中文站：https://zh.wikipedia.org/w/api.php
- 英文站：https://en.wikipedia.org/w/api.php
- Commons：https://commons.wikimedia.org/w/api.php

文章获取使用 action=parse，按需取得正文 HTML、目录、图片名称、页面版本和语言链接。当前文档将 prop=sections 标为弃用，目录信息建议使用 prop=tocdata。[S9] 初版不依赖只返回摘要的接口，因为摘要不足以保留章节和引用。

设计示例参数（需在实现时针对部署站点实测）：

~~~text
action=parse
page=<核实后的页面标题>
prop=text|tocdata|images|revid|langlinks
format=json
formatversion=2
~~~

接口说明核查日期为 2026-10-27。旧教程常见的 api.wikimedia.org Core API 正处于迁移／逐步弃用安排中，因此不将旧端点作为本项目的固定基础。[S10]

### 8.2 保留内嵌引用

本地呈现应保留文章正文、章节层级、引用标记和对应参考文献列表。

处理时需要：

- 清理并适配返回的 HTML，不直接把整个维基网站嵌入 iframe。
- 将站内链接、图片地址和引用锚点改写为本地可用形式。
- 同时显示多个来源时，为每份来源的引用和章节 ID 添加命名空间。
- 本地编辑摘要中的事实引用链接到对应来源，不冒充已经读取了维基列出的全部原始参考文献。
- 保留页面标题、语言、URL、page_id／revision_id（若接口返回）、获取时间与许可说明。

### 8.3 “收集所有图片”的可执行边界

建议理解为：收集**已选香料条目涉及的候选图片清单与元数据**，而非下载整个 Commons、递归遍历所有关联分类或获取所有原始大图。

实施顺序：

1. 从条目获取图片文件名。
2. 分辨实际文件所在站点，查询图片信息；Commons 托管文件使用 Commons API。
3. 用 imageinfo 获取文件 URL、缩略图、尺寸、MIME、描述页和 extmetadata 等信息。[S11]
4. 处理 API continuation，避免只取得第一页结果。
5. 排除图标、装饰图和与本条目无关的图片。
6. 按“整株、部位、干品、粉末、包装、菜品”归类，保留人工调整入口。
7. 默认缓存适合网页阅读的缩略图；选入导出素材时再获取所需分辨率的文件。

“全部”必须对应明确范围：某篇文章某个版本的图片清单，或某个指定分类的一次限定查询。记录获取范围，避免把结果误称为该香料的全部图片。

### 8.4 图片复用与视频素材

每张图片分别保存：

- 文件名称、描述页 URL、原图／缩略图 URL。
- 作者或创作者、来源说明。
- 许可名称、版本与许可链接；原文署名要求。
- 是否做过裁切、加字等修改，以及修改说明。
- 本地文件路径、文件哈希、分辨率与获取时间。
- 用途标签、人工筛选状态与出处核查状态。

Commons 文件的具体要求因文件而异，应按其描述页核实。[S12] 维基文本的复用与翻译也要保留归属、许可和修改说明。[S13]

这些信息直接服务后续视频署名和素材管理。预览图不自动等于可发布素材，其他网站图片也不自动沿用维基的许可。

API 访问使用可识别的 User-Agent、合并查询、串行请求、缓存和失败退避，按官方要求处理限流。[S14]

## 9. 本地翻译与双语阅读

### 9.1 推荐的数据流

来源原文 → 按章节／段落拆分 → 本地后台调用 LM Studio → 校验译文结构 → 缓存 → 网页呈现。

LM Studio 支持 OpenAI 兼容的 /v1/chat/completions，文档示例使用 localhost:1234/v1 作为基础地址。[S15] 实际地址、端口、模型 ID 与认证配置应可设置；网站运行在哪台机器上，也决定 localhost 指向哪里。

建议浏览器只访问本地应用后台，由后台调用 LM Studio。这样获取、翻译和缓存都能集中管理。

### 9.2 三种阅读模式

- **原文**：保持该来源的原语言。
- **译文**：呈现对应的中文机器翻译，注明“本地模型翻译”与人工核实状态。
- **双语**：按同一段落 ID 逐段对照；宽屏可并列，窄屏可上下排列。

中文繁简转换与外文翻译是两种不同处理，应分别记录。英文维基的中文译文也不是中文维基原文。

### 9.3 翻译约束

- 保留标题层级、学名、数字、单位、地名与引用标记。
- 用术语表统一欧芹、芫荽、莳萝等名称，记录地区用词差异。
- 翻译对象先拆成带稳定 ID 的文本块，HTML 与引用结构由程序维护。
- 不让模型增添未提供的事实、引用、化合物名称或功效说明。
- 使用可校验的输出结构，检查段落 ID、数字、单位和引用标记是否缺失。
- 对高价值条目人工复核，尤其是身份、化学成分、栽培数据与文化背景。

翻译缓存键至少关联：来源版本／原文哈希、段落 ID、目标语言、模型标识、翻译提示版本和术语表版本。更换模型时可以明确选择是否重译。

## 10. 搜索的分阶段实现

### 第一层：名称与别名

- 中文名、英文名、学名、地区别称。
- 简繁、大小写和常见拼写归一化。
- 例如输入“欧芹”“Parsley”“欧芹碎”都能到达同一个植物条目，并定位相关形态。

### 第二层：模糊与组合检索

- 英文拼写近似、中文子串／分词、已有标签组合。
- 例如“做烤肉的干叶香草”“籽类＋印度菜”。
- 中文搜索需要明确分词或 n-gram 策略；不能假定 SQLite 默认英文式全文检索会自动解决中文。

前 12–30 个条目，名称和标签可以先在本地 JSON 或 SQLite 中完成检索，英文拼写近似可用 RapidFuzz 等工具。具体库版本在实施时再核实。

### 第三层：可解释的关联浏览

点开“与芹菜相关”，显示“同为伞形科”“同一植物的其他使用部位”等具体关系。相关性可由已核实字段与人工关系生成，第一版无需知识图谱数据库。

### 第四层：语义检索

当问题表达与内容范围扩大后，再加入本地 embedding 模型，将自然语言问题映射到条目与段落。结果继续附上实际匹配内容和出处。

“是否相似”与“能否替代”保持不同的查询意图。替代建议需要菜品与用法条件。

## 11. 推荐的本地技术结构

| 部分 | 建议 | 理由 |
| --- | --- | --- |
| 网页 | HTML／CSS／JavaScript | 初版页面与交互足够，可后续换框架 |
| 本地后台 | Python＋FastAPI | 统一来源请求、翻译、缓存和导出 |
| 目录配置 | JSON | 易读、可版本管理、适合人工维护 |
| 数据库 | SQLite | 单机起步简单，适合条目与来源关系 |
| 原始来源缓存 | HTML／JSON 文件 | 便于保留版本与排查处理问题 |
| 图片 | 文件目录＋元数据记录 | 避免把大图存入数据库 |
| 本地模型 | LM Studio API | 复用本地推理能力 |
| 后续导出 | Markdown／JSON，再加入 PDF | 兼顾阅读、迁移与视频素材工作流 |

这是建议架构，还不是实际安装或运行的项目。

可规划以下目录：

| 目录 | 用途 |
| --- | --- |
| catalog/ | 固定分类、初始条目、别名与关系配置 |
| frontend/ | 页面与样式、交互 |
| backend/ | 来源接入、内容处理、翻译与检索 |
| data/ | SQLite、原文缓存、翻译缓存 |
| media/ | 预览图、选中的原图与元数据 |
| exports/ | 条目导出与视频章节素材包 |
| docs/ | 需求、来源说明与开发记录 |

本地 ID 不依赖页面标题，外部来源与物种／原料之间允许多对多关系。一个香料可能需要多个来源页面；一篇文章也可能同时讲植物、叶与籽。

建议数据库至少区分 plants、ingredients、forms、aliases、relations、sources、source_versions、text_blocks、translations、images、claims、dishes、products。这个列表用于说明关系，实际第一版可以合并部分表，避免一开始建得过重。

## 12. 页面组织

### 首页／目录

- 搜索框。
- 按使用部位浏览。
- 植物科、菜系、风味、形态筛选。
- 条目图片、中文名、英文名与一句话介绍。
- 本地已有内容与可获取内容状态。

### 条目页

- 顶部：中文／英文名、学名、主图与简介。
- 左侧：本地条目目录；阅读来源正文时可以切换到该来源的章节目录。
- 主区：认识它、部位与形态、成分、地理、菜系与菜品、包装。
- 来源区：中文维基、英文维基和其他资料分别切换。
- 阅读区：原文／译文／双语。
- 图库：按图片角色分组，查看出处和许可。
- 相关条目：显示每项的关系理由。
- 导出：当前条目／选中的来源与素材。

编辑整理的“条目概览”与“某一来源的正文”分别标识。既保留百科式阅读，也让使用者看清哪些是原文、哪些是译文、哪些是跨来源整理。

## 13. 逐步实施路线与完成标准

| 阶段 | 做什么 | 可以检查的结果 |
| --- | --- | --- |
| A：内容设计 | 目录、字段、3 个样板条目草案 | 能解释名称、部位、形态、包装和相关关系 |
| B：静态样板 | 12 个目录项、3 个可浏览条目、基础检索 | 名称与别名可查询；页面结构便于阅读 |
| C：单来源接入 | 中文维基正文、章节、引用、图片元数据与缓存 | 引用能跳转，重开先读缓存，来源版本可追溯 |
| D：双语接入 | 英文维基、LM Studio 分段翻译、模式切换 | 段落对齐；数字与引用保留；翻译可缓存 |
| E：关系与多来源 | 关联浏览、指定的补充来源、人工修订入口 | 展示匹配理由，来源与整理内容清楚对应 |
| F：导出与内容生产 | Markdown／JSON／PDF 和章节素材包 | 包含事实出处、图片署名和核实状态 |

阶段 B 的实际样板可先使用少量人工整理内容，验证浏览与搜索方式；阶段 C 再连接真实来源。这样可以在接入更多站点前，先发现分类和页面是否好用。

不预先给出开发工期承诺。每个阶段完成后，用真实条目评估下一步需要的范围。

## 14. 为以后科普视频预留什么

每个已核实条目可导出一份章节素材包：

1. 基本身份与一句话介绍。
2. 认识外观的图片与说明。
3. 使用部位和加工形态。
4. 地理与饮食文化。
5. 代表菜品。
6. 容易混淆的原料。
7. 可选的风味化学扩展。
8. 事实出处、图片署名与许可。
9. 尚待核实的内容列表。

未来 AI 可据此生成讲稿与分镜草稿，事实说明继续关联来源。植物鉴别类配图优先使用核实过的实拍图；示意插画要明确标注。

可考虑的早期选题：

- Parsley flakes 到底是什么？
- 香菜叶与芫荽籽，为什么要分开认识？
- 整粒、粗碎、粉末有什么区别？
- 一种香料为什么会有多个中文和英文名字？

这些是内容选题候选，不代表其脚本已经完成。

## 15. 当前适合确定的默认选择

- 语言：中文优先，英文为第一补充语言。
- 内容：先做植物来源的烹饪香草与香辛料。
- 数据：本地固定目录，正文与图片按需获取并缓存。
- 来源：首批中文维基＋英文维基＋Commons，Wikidata 辅助匹配。
- 模型：LM Studio 先承担翻译；名称搜索和已知关系由程序与数据完成。
- 范围：12 个初始目录项，先深入完成欧芹、香菜／芫荽、芹菜 3 个样板。
- 包装：记录具体产品实例，始终与植物和加工形态区分。
- 后续：稳定条目结构之后，再扩充来源、语义检索、PDF 和视频素材导出。

最先需要通过实际内容检查的是：使用者能否清楚理解“这是什么、用哪个部位、以什么形态使用、和哪些东西有关，以及这些说法来自哪里”。

## 16. 视觉设计补充：统一的图鉴，随材料与历史变化的样式

补充日期：2026-10-27（墨尔本）。

用户希望网站具有较高的美术完成度：叶类采用绿色系，红椒等采用浅红色系；历史名称和由来章节可以结合相关地区与时代的字体和视觉语言；抓取并缓存的内容也应能够适配这些变化。

建议设计方向为“自然史图鉴与文化展签”：以统一、安静、可长期阅读的百科排版承载内容，通过材料色、标题字体和局部装饰区分原料与历史专题。

颜色和历史样式是两条独立轴。一种香料可以有多个部位、形态和文化语境，不为整种植物强行指定一个唯一颜色或唯一时代。

### 16.1 三层样式结构

| 层次 | 决定什么 | 变化范围 |
| --- | --- | --- |
| 全站基础 | 布局、导航、间距、正文、引用、交互 | 始终统一 |
| 材料主题 | 页面浅底、强调色、分隔色、标签底色 | 随所选原料和加工形态变化 |
| 历史展签 | 名称标题、首字、分隔纹样、局部材质 | 随当前展示且有依据的历史专题变化 |

历史主题主要作用于名称、词源与文化历史栏目；正文、表格、引用和操作控件使用稳定的易读字体。

“高级感”的完成标准应落在字距、行长、间距、图像质量、对齐、交互反馈和配色克制上。装饰服务内容，不用大量做旧纹理或不同字体覆盖整页。

### 16.2 调整后的条目视觉字段

- material_theme：材料配色预设。
- ingredient_part 与 processing_form：配色对应的部位和形态。
- history_contexts：一个或多个可选择的历史叙事语境。
- title_treatment：标题排印样式。
- theme_reason：主题选择的说明。
- theme_source：人工设定、审核后的资料提取、用户选择或默认值。
- review_state：建议、已核实、有争议或信息不足。
- rule_version 与 style_pack_version：解析规则和样式版本。
- user_override：用户／编辑明确设定的覆盖值。

这些展示字段与百科事实分开保存。选用某种艺术风格本身不构成历史证据。

## 17. 配色规则：先由原料形态决定，再用内容补充

### 17.1 初始配色建议

以下颜色为设计建议，不是植物分类标准、食品颜色测量结果或最终视觉定稿。

| 材料主题 | 使用示例 | 浅色页面底 | 深色强调 | 对应的暗色页面底 |
| --- | --- | --- | --- | --- |
| 叶绿 | 欧芹叶、干叶碎等 | #F2F6EE | #355A3B | #18211B |
| 籽实暖金 | 芫荽籽等 | #F7F1E5 | #755526 | #242017 |
| 陶土红 | 红椒粉等 | #FBF0EC | #923E32 | #281B19 |
| 木棕 | 肉桂树皮等 | #F5EFE7 | #694C38 | #231E19 |
| 中性图鉴 | 信息不足、混合物、列表页 | 暖灰或纸白 | 中性色 | 中性深灰 |

阅读区可以比页面底色更接近中性纸色。大面积使用低饱和度浅底，把更浓的颜色留给标题、当前选择和少量强调。

同一种植物的不同部位可以采用不同材料主题。例如香菜叶采用叶绿，而芫荽籽采用暖金。进入物种总览、同时比较多个形态时，使用中性背景，并在各形态区域分别呈现色彩。

“叶类”不等于必须绿色，“辣椒”也不等于必须红色。青椒、不同成熟状态、不同加工形态均可能不同；分类提供默认值，具体原料记录可以覆盖它。

### 17.2 配色来源的优先级

1. 编辑或用户明确设置的原料形态主题。
2. 已核实的具体部位／加工形态配色。
3. 人工维护的材料分类默认值。
4. 从文字或图片提取并经审核的建议。
5. 中性图鉴主题。

初始目录数量有限，前 12–30 个条目的主题可以直接人工设定，既快也容易保持协调。后续的自动提取用于扩展目录和发现待核实信息。

### 17.3 关键词怎样辅助

“绿色”“红色”“褐色”等词应先绑定到描述对象和部位，保留所在句子，再形成建议。多语言来源可统一映射到颜色标签，不限于中文的“色”字。

例如，资料写“叶绿色、花白色、成熟果实变红”，不能只取最先或最频繁出现的颜色作为整页背景。烹饪后的菜色、包装颜色也不等于原料本身的颜色。

如果以后从图片取色，需要先选择对应原料的有效区域，排除背景、盘子、手、包装和光照影响；提取结果再映射到少量人工设计的色板。直接把整张照片的主色当页面色，容易受到摄影背景影响。

### 17.4 可读性

正文、控件和图表不能只靠颜色表示类别。配色要同时提供名称或文字标签。主题的浅色与暗色版本分别检查文字与背景对比；WCAG 的普通文本最低对比要求通常为 4.5:1，大号文本为 3:1。[S20]

## 18. 字体与历史风格：按文字用途与叙事语境选择

### 18.1 网页字体的能力

网页并不只支持宋体、楷体或少数系统字体。CSS 的 @font-face 可以加载自定义字体，网页字体常采用 WOFF2。[S18]

决定能否展示的主要条件是：

- 有可用的字体文件。
- 字体确实覆盖要显示的字符与字形。
- 授权允许相应的网页使用和分发方式。
- 浏览器能够加载字体，缺字或加载失败时有合适回退。

“篆书”“隶书”“楷书”等视觉风格可以由适合的字体实现，但具体古文字字符、异体字或铭文未必有相应字形。需要时可以展示有出处的原文图像，并同时提供现代文字转写，保证名称仍可搜索、复制和阅读。

### 18.2 区分历史复原和现代设计意象

| 用途 | 合适处理 |
| --- | --- |
| 有可靠出处的历史原文或古名 | 显示原文／转写与出处，必要时展示文献图像 |
| 受某种书写或印刷传统启发的现代标题 | 标为风格或排印意象，不称为古代原样 |
| 现代中文名称、英文名称和学名 | 保持语义准确，按文字系统选择字体 |
| 正文、按钮、表格、脚注 | 以阅读和操作为主，保持统一 |

Times New Roman 可以营造经典印刷感，但它于 1932 年在《泰晤士报》启用，不能作为中世纪字体的历史证据。[S19]

同样，现代采用宋体、楷体或书法字体并不自动证明某个名称的年代。后续若要做具体时代的字体考据，需要核实相关文献和字形，而不是仅根据字体名字推断。

### 18.3 按语言与文字系统匹配

- 中文段落使用覆盖中文的正文字体。
- 英文、拉丁学名等分别使用合适的拉丁字母字体；字体风格和文本语言是两件事。
- 希腊语内容需要覆盖希腊字母的字体；不能因为英文标题使用衬线体就称为古希腊文字。
- 阿拉伯文等来源需要正确的文字方向与字形处理；不能用拉丁字母的装饰字体代替。
- 双语对照时，每一段按实际语言标注并加载相应字体。

本地正式实现优先保存获准分发的字体及其许可信息，保证离线可用；中文大字库可在授权允许时分块或按需加载。

### 18.4 文化样式的作用范围

一味香料可能在多个地区和时代流通。原生分布、早期使用、贸易记录、传入某地区和现代菜系用途应作为多个历史事件保存。

建议在“名称与历史”中切换有依据的专题语境，而不是只给整株植物贴上“欧洲中世纪”或“中国古代”一个固定标签。

没有足够证据时，使用中性的植物图谱风格。明确展示的“中文书写意象”“西文书页意象”“拉丁铭文意象”等设计试样，不代表该原料实际起源于这些文化或时代。

## 19. 年份、地点与关键词：提取候选事件，再决定样式

用户提出的“最早年份＋离‘起源／最初’最近的地区”可作为低成本候选生成规则，但不适合作为直接控制整页风格的最终规则。

### 19.1 常见歧义

| 文本信息 | 可能代表什么 |
| --- | --- |
| 最早出现的年份 | 引用出版年、植物命名年、考古年代、历史事件年代 |
| “在某地发现” | 考古出土地点，未必是原产地 |
| “最初传入欧洲” | 一个传播事件，未必是植物起源 |
| “原产某地区” | 生物地理说明，未必是最早食用或种植地点 |
| “古代曾用于某菜” | 使用传统，未必代表今日主要菜系 |
| 一个中文译文中的最近地名 | 翻译后的语序结果，未必对应原文关系 |

公元前、世纪、朝代、时间区间和“至少已有”等不确定表述，需要保留原文，不能都压缩成一个精确年份。

### 19.2 推荐处理流程

来源段落 → 候选线索 → 结构化事件 → 出处与关系检查 → 人工核实 → 历史专题 → 视觉样式。

可由本地模型帮助提取以下字段，但模型不能自行补写年代或地点：

- source_id、source_revision、block_id。
- 原文证据片段及字符范围。
- 事件类型：原生、栽培、使用、贸易、传播、文献记载、植物命名、出版或未知。
- 原始时间表达；能确定时记录时间区间和不确定性。
- 地点名称与标准化地理标识，无法确定时留空。
- 文化或文献语境。
- 核实状态与编辑备注。

检查时应回到原文证据，必要时核对原始参考文献。关键词和距离仅帮助找候选，不直接生成历史结论。

### 19.3 历史样式的优先级

1. 用户当前选择的、已经核实的历史专题。
2. 编辑设定并附有依据的推荐专题。
3. 已核实事件对应的展示预设。
4. 中性植物图谱。

未核实的自动提取只进入建议列表。不要为视觉切换伪造可信度百分比，也不要把“自动提取”标成“已证实”。

## 20. 让抓取、缓存和样式互不干扰

### 20.1 分开保存四类内容

| 内容 | 缓存／版本依据 |
| --- | --- |
| 来源原文 | 来源、页面、语言、版本或文本哈希 |
| 翻译 | 原文版本、模型、提示与术语表版本 |
| 结构化条目与事件 | 本地条目、编辑记录、核实状态 |
| 主题设置 | 材料主题、历史专题、规则与样式包版本 |

换配色不需要重新抓取或翻译。换来源、切换原文和译文，也不应让已经确认的条目颜色反复改变。

### 20.2 本地记录示例

以下为结构示意，不包含已经核实的历史事件：

“没有历史专题”是正常状态，网页仍可使用完整的基础样式。

### 20.3 页面渲染

网页根据本地材料主题和标题样式选择预设，来源正文只进入指定的阅读区域。抓取内容中的样式和脚本不应覆盖应用自身的排版。

统一的阅读区域负责标题层级、段落、表格、引文和脚注。材料主题通过少量 CSS 设计变量控制背景、强调色和分隔色；历史样式通过独立的标题类控制。

人工修改不被自动更新覆盖。来源变化后，重新提取的建议保留来源版本，并提示哪些事件可能需要复核。

### 20.4 用户选择

提供中性／标准阅读模式，允许读者关闭文化装饰。主题是浏览辅助，不妨碍查找事实、复制内容、双语对照和导出。

## 21. 对实施顺序的补充

先设计少量高质量的材料色板和排印样式，在真实样板条目中检查，再扩大自动化。

1. 完成基础排版与 4 个材料色板：叶绿、籽实暖金、陶土红、木棕。
2. 用人工维护的 3 个样板条目检查不同部位与形态的切换。
3. 设计中性图谱、中文书写、西文书页等标题试样；这些首先属于现代设计预设。
4. 接入抓取内容，检查长标题、中文、英文、表格、引用与缺图状态。
5. 加入带出处的历史事件模型。
6. 再让本地模型提取历史与颜色候选，逐项审核后使用。

后续网页验收应包含：

- 同一植物不同形态可以采用不同配色。
- 色板变化时导航、引用和正文仍一致、可读。
- 公元前、世纪与模糊年代不会被误识别成精确年份。
- 文献出版年不会触发古代／现代主题切换。
- 来源切换或翻译更新不会覆盖人工设定。
- 字体加载失败时名称仍可显示、搜索和复制。
- 小屏幕、暗色外观和键盘操作可以使用。
- 历史风格有明确依据，或清楚标为设计意象。
